Architecture challenge

Legacy batch ingestion pipelines created data latency, limited operational visibility and frequently failed when external vendors changed their file schemas without notice. The architecture needed to support multiple vendor formats and concurrent ingestion spikes while keeping onboarding repeatable.

Architecture strategy

The solution uses an event-driven Azure Medallion Lakehouse architecture. Event Grid and Azure Functions coordinate file-arrival processing; ADLS Gen2 provides the landing location; metadata-driven Databricks notebooks parse, transform and route data through Bronze, Silver and Gold layers using Delta Lake.

Metadata-driven processing

The Databricks notebooks use metadata to drive parsing, transformation and routing rather than relying on a separate hard-coded pipeline for every vendor. This creates a reusable onboarding pattern while preserving the ability to handle source-specific formats.

Schema inference and evolution

A lightweight AI orchestration layer uses automated schema inference to detect and log schema drift and alert engineering teams. Dynamic, non-breaking schema evolution and partition tuning address changing vendor formats and concurrent ingestion spikes.

Architecture boundaries

The design separates file landing, event coordination, processing, schema management and downstream analytics. This separation helps isolate changes in upstream vendor files from the broader analytics platform.

Measured outcomes

The project summary reports that data delivery latency was reduced from hours to minutes, data-related incidents were reduced by 85%, and vendor onboarding was automated. The current-role summary also reports an 85% reduction in ingestion failures and a 90% reduction in manual data engineering overhead.

Architecture decisions & trade-offs

These records explain the reasoning behind the pattern and the trade-offs an architect should make explicit. They distinguish documented project choices from general design implications.

Event-driven coordination vs. polling

File-arrival events reduce dependence on repeated directory checks and support responsive processing. The trade-off is that event delivery, retries and duplicate notifications must be handled safely.

Portfolio evidence: Event Grid and Azure Functions are part of the described solution.

Metadata-driven notebooks vs. vendor-specific pipelines

Shared processing logic makes onboarding more repeatable and reduces duplicated code. The trade-off is a stronger need for governed metadata, validation and controlled vendor-specific exceptions.

Portfolio evidence: metadata-driven Databricks notebooks are described.

Raw landing + Medallion layers vs. direct transformation

Keeping raw files and separating Bronze, Silver and Gold improves traceability and supports reprocessing. The trade-off is additional storage and lifecycle management.

Portfolio evidence: ADLS Gen2, Delta Lake and Bronze/Silver/Gold are described.

Schema evolution vs. strict rejection

Controlled evolution can keep compatible source changes moving while surfacing drift. The trade-off is that unreviewed changes can alter downstream meaning; breaking changes need quarantine or review.

Portfolio evidence: automated schema inference, drift logging and dynamic non-breaking evolution are described.

Architect’s takeaway

The key architecture idea is repeatability: use event-driven coordination and metadata-driven processing to onboard varied sources through a consistent lakehouse pattern, while making schema changes visible and manageable.

Scope note: This case study summarizes the architecture and outcomes described in the professional experience. Implementation details are kept at a level suitable for a public portfolio.
