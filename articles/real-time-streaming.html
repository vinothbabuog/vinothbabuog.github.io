Architecture challenge

Fluctuating volumes of gameplay telemetry and user events caused analytical dashboards to fall hours out of sync. This limited the usefulness of real-time fraud detection and player monitoring.

Architecture strategy

The platform combines Azure Event Hubs and Spark Structured Streaming with a Medallion Lakehouse architecture. PySpark streaming applications process thousands of telemetry events per second and transform raw event streams into operational Gold-tier player metrics.

Streaming processing design

Sessionization and aggregation frameworks convert event-level telemetry into metrics suitable for operational analytics. The architecture uses stateful checkpointing, watermarking and idempotent sink logic to manage duplicate processing, out-of-order events and late-arriving data.

Reliability considerations

Checkpointing supports recovery of streaming state; watermarking defines how late events are handled; idempotent sink logic helps prevent duplicate outputs. These mechanisms address the stream-processing gaps and data duplication challenges described in the project résumé.

Analytics and operational use

The resulting Gold-tier metrics support real-time player monitoring and analytics. The résumé also describes machine-learning heuristics and anomaly detection over streaming sessions for identifying suspicious transactions and anomalous behavior patterns.

Measured outcomes

The project processed thousands of telemetry events per second and reduced processing latency to sub-second windows. The résumé describes this as enabling operational real-time monitoring and improving fraud-detection accuracy.

Architecture decisions & trade-offs

These records explain the reasoning behind the pattern and the trade-offs an architect should make explicit. They distinguish documented project choices from general design implications.

Streaming vs. scheduled batch

Streaming supports operational use cases where hours-old data is not useful. The trade-off is more operational complexity and careful state/recovery management; batch remains suitable for non-urgent workloads.

Portfolio evidence: Event Hubs and Spark Structured Streaming process thousands of events per second.

Event-time watermarks vs. immediate-only processing

Watermarks allow bounded late-arriving events to be incorporated into aggregations. The trade-off is a latency/completeness balance and an explicit policy for events arriving beyond the allowed lateness.

Portfolio evidence: watermarking is described in the streaming design.

Checkpointing vs. stateless restart

Checkpointing preserves streaming progress and state for recovery. The trade-off is checkpoint lifecycle, compatibility and storage management.

Portfolio evidence: stateful checkpointing is described.

Idempotent writes vs. at-least-once duplicate risk

Idempotent sink logic helps prevent duplicate outputs when processing is retried. The trade-off is additional keying or merge logic and a clear definition of event identity.

Portfolio evidence: idempotent sink logic is described.

Architect’s takeaway

A real-time architecture must account for event volume, event-time behavior, recovery and downstream consumption—not just the speed of the streaming engine.
